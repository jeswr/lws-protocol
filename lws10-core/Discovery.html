Storage Description Resource

A storage description resource describes a storage, its capabilities, and its service endpoints. Its abstract model is RDF. The optional fixed JSON representation is a specialization of a Controlled Identifier document [[!CID-1.0]]. Other representations do not claim to be CID documents.

Data Model

The node identifying the storage MUST be its canonical URI and MUST have rdf:type lws:Storage. It MUST link through did:service to a service of type lws:StorageRoot. Exactly one such root service MUST be present. Each service MUST have an IRI identifier, one or more types, and a did:serviceEndpoint IRI. Other services MAY be present.

The prefixes lws: and did: expand to https://www.w3.org/ns/lws# and https://www.w3.org/ns/did#. The latter service properties are the RDF mappings used by the CID context. A storage's capabilities are linked using lws:capability; each capability MUST have a type and MAY have an IRI identifier and extension properties.

Representation capabilities MUST be supplied for the storage description and containers, and for access request/grant objects when those services are implemented. The Storage and Container classes MUST each have an unscoped baseline capability; service-scoped records may override it for their service. Implemented notification suites MUST advertise capabilities for their notification and subscription classes, subject to the suite-defined formats. The requirements in define their scope and meaning.

Discovery and Binding

Responses to GET and HEAD on storage resources MUST include a Link header targeting the canonical storage URI, with rel="https://www.w3.org/ns/lws#storage". This relation identifies storage membership independently of path layout.

A GET on that URI MUST return the storage description using HTTP content negotiation. A client retrieving it for the first time MUST advertise the formats it can process, including text/turtle and application/ld+json for an RDF-capable client. Discovery does not require the client to read the capability list before making that request. A profile-specific client with no supported alternative MUST report a 406 response as an incompatible configuration.

Storage Capabilities

The following Turtle-only configuration advertises representations for its description and container listings. This is a non-normative example; access services add their own representation records when implemented.

@prefix lws: <https://www.w3.org/ns/lws#> .
@prefix did: <https://www.w3.org/ns/did#> .

<https://storage.example/> a lws:Storage ;
    did:service <https://storage.example/#root-service> ;
    lws:capability [ a lws:RepresentationCapability ;
        lws:appliesTo lws:Storage ; lws:produces "text/turtle" ],
      [ a lws:RepresentationCapability ;
        lws:appliesTo lws:Container ; lws:produces "text/turtle" ] .
<https://storage.example/#root-service> a lws:StorageRoot ;
    did:serviceEndpoint <https://storage.example/root/> .

Storage Services

The root service's endpoint MUST be the URI of the storage root container. An access service MUST advertise its supported policy profiles using dcterms:conformsTo. A policy profile and a representation profile are independent: the same policy may be exchanged in Turtle or JSON-LD.

Storage Description Representation

When application/lws+cid is offered, the document MUST conform to [[!CID-1.0]] and the RDF model above. Its @context array MUST begin with https://www.w3.org/ns/cid/v1 and https://www.w3.org/ns/lws/v1, in that order. The JSON keys id, type, service, serviceEndpoint, and capability represent the corresponding identifiers, types, service relations, endpoints, and capabilities. service and capability MUST be arrays, even for a single entry. Service objects MUST include id, type, and serviceEndpoint. Other RDF serializations have no @context or JSON array requirement.

The versioned LWS context must be published with the vocabulary additions before deploying this draft's fixed JSON format. The conformance fixtures bundle the draft context and resolve it locally; they do not depend on an unpublished change at the W3C URL.
