This section defines a mechanism for identifying agents and end users that interact with a linked web storage server. This specification does not mandate a particular format for an authentication credential, though it does describe how existing identity systems can be used in conjunction with the linked web storage authorization framework.

Authentication Credential Data Model

The data model described in this section outlines the requirements for any concrete serialization of an authentication credential.

An authentication credential MUST include tamper evident claims about a subject, including:

  • subject REQUIRED — an identifier for an end user. This MUST be a URI.
  • issuer REQUIRED — an identifier for the entity that issued the authentication credential. This MUST be a URI.
  • client REQUIRED — an identifier for a client application. This SHOULD be a URI.
  • audience restriction RECOMMENDED — a list of values that SHOULD include an authorization server identifier.

Authentication Credential Validation

Validation of an authentication credential requires a trust relationship between the verifier and issuer of the credential. Each authentication suite MUST define an in-band mechanism by which a verifier, without prior configuration, discovers the verification material for a credential and confirms that the issuer is authorized to make claims about the subject, starting from identifiers in the credential (for example, by dereferencing the subject or issuer URI). A verifier MAY apply locally configured policy, such as allow or deny lists of issuers, to restrict which validated credentials it accepts; such out-of-band configuration MUST NOT be required in order to validate a credential.

An authentication credential MUST be signed. It is RECOMMENDED that the signature uses asymmetric cryptography.

Authentication Credential Type Identifiers

Each authentication suite MUST be associated with a token type URI. An authentication suite SHOULD use a URI defined in the IANA "OAuth URI" registry.
